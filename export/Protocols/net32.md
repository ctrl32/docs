# net32 — the ctrl32 device network

**net32 is our network**: panels, headless nodes and Linux devices
working as **one system** — the backbone ctrl32 builds home
automation and small plants on. One device measures a temperature;
another shows it on its screen and writes the setpoint back. No PLC
in the middle, no register maps, no polling tables, no cloud — the
devices keep each other in step over WiFi, ethernet or CAN, and
**every device runs its own logic**, so the house keeps working when
the network does not.

Inside net32, sharing follows one rule: **every shared variable has
exactly one owner.** The owner measures or computes the value; every
other device subscribes to it. Writes go the other way as *commands*
to the owner — the local copy never pretends, it only ever shows the
owner's state.

## What it feels like

- On the **owner**, a shared variable is an ordinary local variable
  with a *published* checkbox — publishing changes nothing about how
  the device itself uses it.
- On a **subscriber**, the variable names its source: the owner's
  node number and the variable's name there. It lands in the variable
  table like any Modbus or +7 value and everything downstream
  (screens, logic, alarms, trends, WEBview) treats it normally.
- A setpoint field or a switch bound to a subscribed variable writes
  **to the owner**. The new value appears when the owner confirms it —
  the same honest behaviour WEBview and MQTT writes have always had.

## The link is honest

Networks drop out. net32 is built so a dropout is *visible* and never
*dangerous*:

- Every subscription carries freshness. When the owner falls silent
  past the stale timeout, the last good value stays readable but the
  peer's **health variable** drops to 0 — a `bool` you bind on the
  net32 page and use in logic and on screens (dark lamps, a red
  banner, heaters off).
- Writes toward a silent peer are refused on the spot, never queued —
  a command from ten minutes ago must not fire when the link heals.
- Each device fingerprints its published list. A device hearing a
  layout it does not expect — half the pair updated, half not — marks
  those variables **bad** instead of reading garbage, and says so in
  the diagnostic buffer. Update the second device and everything
  heals by itself.
- Local logic runs on local variables. A device that loses the
  network keeps controlling whatever it owns.

## Transports

| Transport | Where | Notes |
|:---|:---|:---:|
| **UDP** (WiFi / ethernet) | every ctrl32 device | on by default |
| **CAN** | devices with a CAN bus | no network stack needed, coexists with CANopen |

Values travel on change (the variable's deadband applies) plus a
periodic refresh, roughly once a second. On WiFi, where access
points commonly filter multicast, add the peer's address to the
**Peer addresses** list — devices also learn each other's addresses
from what they hear, so one fixed address per pair is enough.

## The system project

The natural way to build a net32 system is **one project holding
every device**. Right-click the project name in the device tree and
pick **Add device (make a net32 system)** — the open project becomes
the first device and the installation grows from there, all in a
single `.prj32` file. Every device shows as **its own full project
tree** — screens, logic, variables, buses — so the whole
installation is visible at once; the active device is the one you
edit, and a click anywhere in another device's tree switches to it.
One **Save** stores the whole system.

![Every device is its own project tree — the active one is live](img/net32-tree.webp){: .sb-center}

Clicking the system name at the top of the tree opens the **net32
canvas**: one card per device, its published variables as pins on
the right, its subscriptions arriving on the left. **Drag a line
from a published pin onto another card and the subscription exists**
— the local variable on the subscriber is created for you, named and
typed to match. Everything shared between two devices rides **one
wire** with the count on it; clicking the wire opens its variable
list, where single subscriptions are removed and the peer's health
variable is added. A checkbox on the card publishes a variable, and
while the canvas is open the wire shows the live truth — green when
both ends are alive and speaking the expected layout, red when one
falls silent.

![net32 system canvas](img/net32-system.webp){: .sb-center}

In a system project the remote lists of every device are **written
by the editor at build time** from what the canvas shows — the two
sides of every pair are generated by the same hand, so the
fingerprints that protect a half-updated pair can never disagree at
the desk. There is nothing to paste and nothing to keep in step.

**Deploy all** builds every device's pack and uploads each one over
its own connection — network devices by their address, USB devices
by their port — with a named result row per device.

![Deploy all — one result row per device](img/net32-deploy.webp){: .sb-center}

While the canvas is open the editor also **listens** to the system's
own traffic: lines turn green when both ends are alive and speaking
the expected layout, red when a peer falls silent — the same honest
freshness the devices themselves act on.

A standalone single-device project can still join a system by hand —
the per-device setup below remains fully supported, and it is the
form the system project generates under the hood.

## Setting it up (single device)

1. Right-click the **Ethernet** or **WiFi** interface in the device
   tree and pick **Add net32…**
2. Give the device its **node number** (1–254, unique) and a
   **system** number — devices only hear their own system, so two
   installations next to each other stay separate.
3. Tick **published** on the variables this device owns and shares.
4. For each remote device, add its node under **Remote lists** and
   paste its published list (`name:type`, one per line, in the
   owner's order). **Create/update subscriptions** then makes the
   local variables in one press, and **Create health variable** adds
   the peer's `bool`.
5. *Download to board.* net32 is part of the pack — adding a variable
   or a peer never needs new firmware.

Limits: 64 published and 64 subscribed variables per device, 32 peer
addresses. Everything over a limit — and every inconsistency, like
subscribing to a name the remote list does not carry — is refused
when the project builds, with the reason spelled out.

## Good to know

- The remote list you paste is the contract: both sides carry it, and
  the fingerprint computed from it is what protects a half-updated
  pair. When you add a published variable on the owner, update the
  subscriber's remote list too — until then the subscriber shows
  *bad* instead of guessing.
- Shared variables are bool, the integers, real and the 64-bit kinds
  (LInt, ULInt, LReal). A 64-bit variable takes two of the 64 wire
  slots a device publishes, and it sits on an even slot so one CAN
  frame carries it whole - the editor counts the slots for you.
  Strings stay local.
- net32 connects **ctrl32 devices** to each other. To talk to a
  foreign PLC use [Modbus](/docs/buses/modbus/) or [+7](/docs/buses/plus7/); to feed a
  SCADA or a home dashboard use MQTT or the OPC UA server.
- Stopping equipment over the network is **not a safety function**.
  E-stop stays hard-wired.
